# 反例库（决策前扫一眼，不是事后追责）

> 规则告诉你"该怎么做"，反例告诉你"不然会怎样"。人对后果的记忆强于对规则的记忆。
> 用法：开工前、评审时、想跳过某条规则时，扫一遍标题；中了的看判据。
> 全部来自一个真实项目（15 天 / 198 次提交 / 28 条错因），已脱敏为通用形态。

## 1. 两个"计数"共用一张表

- **场景**：页面上有"打卡天数"和"今日复习进度"，都从同一张记录表算。
- **错误推理**：都是"今天做了多少"，一张表够用，不必分开。
- **后果**：模拟面试也调了同一个计数，复习页显示"11 / 10"——超过上限。花一轮改表结构。
- **判据**：出现两个以上计数，先写清各自定义域与互斥关系，再动手。

## 2. 用数据字段解释界面文案

- **场景**：一列叫"未学习"，我按"库里还有多少道没学过"填。
- **错误推理**：列名对应状态字段，`reps === 0` 就是"未学习"，逻辑自洽。
- **后果**：用户要的是"今天还剩几道没学"。连纠三轮，最后用户被迫给出界面结构建议。
- **判据**：界面文案按"用户拿它做什么决策"定义，不按数据字段定义。含糊就列两个选项让用户选。

## 3. 兜底成功，当成没出事

- **场景**：在线语音失败时自动回退本地引擎，返回成功。
- **错误推理**：有降级路径，用户不会中断，等于没问题。
- **后果**：在线通道连续 4 天一次没成功，用户听到的一直是本地音色，界面一个字没提示。第 4 天才被发现。
- **判据**：任何静默降级必须把 `{from, reason}` 透传到界面。"兜底成功"≠"没出事"。

## 4. 让用户执行我自己没跑过的东西

- **场景**：给了一个 `.cmd` 让用户双击，里面写了中文注释。
- **错误推理**：命令逻辑是对的，双击就跑，最省事。
- **后果**：cmd.exe 按 GBK 解析 UTF-8，乱码被当命令执行，用户机器"输入任何东西都闪退"——唯一一次 P0 事故。
- **判据**：先看解释器——cmd.exe 解释的零非 ASCII（含注释）；bash 解释的可留中文但须 UTF-8。共同：可撤销、优先给命令不给文件。

## 5. 把"我没找到"说成"不存在"

- **场景**：用户问能不能不花自己的 API Key。我查了三处就说"没有可编程入口，这条路走不通"。
- **错误推理**：PATH、文档索引、安装根目录都查了，没有就是没有。
- **后果**：用户一句话质疑，我再查 `app.asar.unpacked`，发现内置 CLI——上一轮结论当场作废。整条产品路线差点没做。
- **判据**：说"做不到"必须附穷举清单（查了什么、没查什么、下一步还能怎么查）。清单有缺项只能说"暂未找到"。

## 6. 验证需要用户先停下来

- **场景**：验收脚本要读写真实数据库，而正式运行占着单实例锁。
- **错误推理**：让用户关掉应用再跑，反正就几秒。
- **后果**：整个开发期阻塞 5 次；其中 2 轮用户只回了"关了"两个字，这两轮的全部价值就是替我解锁环境。
- **判据**：同一条验证需要"用户先退出应用"才能跑，是设计缺陷不是操作步骤。测试环境必须与运行环境并存。

## 7. 漏跑一层，没人知道

- **场景**：改了控件名，忘了同步冒烟脚本里的选择器。
- **错误推理**：单测绿了、真机验收绿了，交付没问题。
- **后果**：冒烟脚本一直打印 FAIL，隔了整整一轮交付才发现。没有任何机制提醒"第三层没跑"。
- **判据**：交付说明只点名「与本次改动相关」的未跑层。不相关的层不提——提了就是仪式。最好让门禁去查这个记录。

## 8. 同一个数字散落在多个文档

- **场景**：错因本从 23 条补到 28 条，占比从 43% 变 36%。
- **错误推理**：改了主报告就行，其他地方是引用。
- **后果**：`01` 判决表、DoD 清单、raw 素材、另一个仓库的 README 共 **13 处**仍是旧数字，靠 grep 才发现。
- **判据**：改任何统计数字前先 grep 全库；改完再 grep 一次确认。数字只留一个权威来源，其他写"见 X"。

## 9. 查询函数里做副作用

- **场景**：取"当前该复习哪张卡"的函数，顺手把队首 `shift` 掉了。
- **错误推理**：反正取出来就要用，一起做了省事。
- **后果**：这个函数在渲染和评分两处都被调用，每渲染一次消费一次——同一道题永远卡在队首，队列走不完。
- **判据**：查询函数不许有副作用。"取当前值"和"推进队列"必须分开，哪怕只多一个状态位。

## 10. 外部服务"正常返回但内容为空"

- **场景**：调推理模型写面试官提问，`finish_reason=stop`、`content=""`。
- **错误推理**：HTTP 200 就是成功，空内容按异常处理（抛给用户）。
- **后果**：模型的输出预算全花在思考上，实测 12 次请求里 5 次不可用（约 42%）。客户端零重试 + 严格解析 = 一次抖动一次中断，还产生 3 条重复记录。
- **判据**：与 LLM 的结构化契约按"可能空、可能不守格式"设计三层：自动重试 → 结构化输出 → 解析兜底。

## 11. 提一个不存在的待决项

- **场景**：核对完功能后，向用户提"历史数据要不要回填？"
- **错误推理**：数据一致性是个风险点，先问清楚显得周全。
- **后果**：用户回"什么回填不回填，我没太搞清楚"。查完发现库里根本没有不一致的数据——**这个问题不存在**，我在用伪选择题消耗他的判断力。
- **判据**：待决项必须来自真实分歧。两个选项我都能自己选且风险相同时，直接选并标注"已默认，不同意就说"。

## 12. 把估值写成实测

- **场景**：写交付说明时，凭印象写"改了 74 行""约 9800 字"。
- **错误推理**：量级差不多，写个大概数不影响结论。
- **后果**：实际是 89 行、15126 字。数字一错，"可核验"就成了空话——读者按我的数去核对，永远对不上。
- **判据**：任何数字先跑命令量一次再写；量不了就写"约"并注明估算口径。这一条对我自己也适用。

---

## 怎么用这份库

- **开工前**：扫标题，中了的看判据。
- **评审/复盘时**：新踩的坑按"场景 / 错误推理 / 后果 / 判据"补一条，不要写成流水账。
- **删的条件**：某条连续两个项目没被触发过，且举不出它拦下问题的实例 → 删。

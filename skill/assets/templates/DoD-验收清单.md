# DoD 验收清单（<项目名> · <日期> · <需求名>）

> 判定规则：一处勾选 = 一段命令原文 + 末行输出。只写「已测试」「应该没问题」不算勾（阶段五 / V8）。

## 0. 交付四件套（缺一件不算交付，范式 5.1）

- [ ] **Changed Files**：逐行贴出本次改动文件清单，与 `git status` 一致。
- [ ] **Verification**：每条命令 + 末行输出原文，如 `npm test → test 25/25 PASS`。
- [ ] **Visual Proof**：截图路径 `<截图目录>/<日期>-L4-<场景>.png`；非 UI 任务写「无 UI 改动」。
- [ ] **Behavioral**：关键行为 1–3 条，「做了什么操作 → 看到什么结果」。

## 1. 五层验证（一层都不能用别的层代替）

### L1 单测
- [ ] 命令：`<单测命令>`（示例 `npm test`）
- [ ] 通过标志：末行 `test <N>/<N> PASS` 且 N>0、FAIL=0
- [ ] 防：只跑语法检查就宣称"测过了"（M-008）

### L2 交互冒烟
- [ ] 命令：`<冒烟命令>`（示例 `npm run verify:ui`，必须真跑应用，不是 `node --check`）
- [ ] 通过标志：输出 `<UI SMOKE OK>`；出现 `FAIL` 即不通过
- [ ] 防：控件改名但冒烟断言没同步，绿了一轮才发现（M-001 / M-008）

### L3 持久化
- [ ] 命令：改一条数据 → 完全退出进程（不是关窗口）→ 重启 → 再读同一字段；或 `<持久化脚本>`
- [ ] 通过标志：重启后读到的值 = 退出前的值，且不等于默认值
- [ ] 防：内存里对、落库丢 / 读的是常量默认值（M-010 的跨运行状态陷阱）

### L4 渲染
- [ ] 命令：`<截图命令>`，产物存 `<截图目录>`
- [ ] 通过标志：打开截图，`<预期控件>` 可见、数量与位置符合 spec；空白图 / 黑图 / 被遮挡 = 未通过
- [ ] 防：逻辑正确但界面没画出来（M-018 / M-002）

### L5 真机验收
- [ ] 命令：`<验收命令>`（示例 `node tests/acceptance-live.js`）
- [ ] 通过标志：末行 `<N>/<N> PASS`，且 N ≥ 本次 spec 新增断言数
- [ ] 防：没跑全链路就宣称完成（V8 / M-008）

## 2. 断言有效性自查（跑验收之前先过，五项）

> 前两项防「假绿」（断言永远为真，测不出退化），后三项防「假红」（环境问题被误判成回归）。
> 本项目 28 条错因里 10 条出在这里，占 36%（补录 5 条流程类之前的 23 条口径下是 43%）。

### 2.1 区分力（防"永远为真"）

- [ ] 写下三个数：**正常值 / 故障值 / 噪声**。正常与故障的差距小于噪声量级 → 重写断言（V1 / M-012）
- [ ] 性能类断言用的是**每次唯一的输入**（带时间戳或先清缓存），不是固定字符串；否则跑第二遍命中缓存，从此永远为真（V2 / M-007）

### 2.2 反向验证（防"从来没红过"）

- [ ] 挑一条关键断言，把被测代码**故意改坏一处**，确认它变红；不变红就说明这条断言没测到点子上，当场修（V1）

### 2.3 假红三查（防"环境报警"）

- [ ] **窗口遮挡**：被测窗口没有最小化、没有被其他窗口盖住 —— 合成器不出帧会导致卡死或黑图（M-009）。
- [ ] **跨运行状态**：同一条验收命令连跑两次，第二次仍绿 —— 第二次变红说明脚本依赖上次残留数据，是脚本 bug 不是代码 bug（M-010）。
- [ ] **外部配额**：今天外部服务配额没用完；配额耗尽时断言必须走 SKIP 分支，且 SKIP ≠ PASS（M-014）。

## 3. 未跑层点名（只报相关的）

- [ ] 先写一句「本次改动影响哪几层」：改 renderer → L2/L4；改 src → L1/L3；改数据结构 → 全部
- [ ] 只对这几层写「跑了 / 没跑」，没跑的写 `未跑：L<n>（原因）`
- [ ] **不相关的层不用提**。写「未跑：完整测试套件」但本次只改一行文案 → 属于仪式化
- [ ] 判据：这段话换到别的任务里也成立 → 是废话，删掉重写（V8 / M-008）

- [ ] 「不方便跑」「这台机器跑不了」不构成跳过理由；确实跑不了，按上面格式点名，不许省略。
- [ ] 所有"通过"结论后面都带命令原文 + 末行输出，禁止只写结论（范式阶段五）。

## 4. 数据与回滚

- [ ] 任何删除/覆盖 `<数据目录>` 之前，已备份到 `<备份目录>` 并确认备份文件存在（M-004 / DT4）。
- [ ] 批量改动前已打 checkpoint：`git commit -m "chore: checkpoint before <改动名>"`（范式 4.1）。
- [ ] 验收不过的处置已写明：`git reset --hard <checkpoint>` 或弃分支，不手工逐文件回退（范式 4.2）。

## 5. 提交与范围

- [ ] `git status` 确认暂存区只含本次改动，没有顺手带上的无关文件（00-A4 提交信息即任务日志）。
- [ ] 提交信息含三要素：为什么改 / 边界 / 验证过什么（范式 4.3）。
- [ ] 未使用 `--no-verify`；git 成败用 `git log -1` / `git status` 坐实，没接管道（CO5 / M-003）。
- [ ] 改动文件 ⊆ spec「任务拆分」表；超出就先回去改 spec，不在代码里扩范围（范式 1.2）。
- [ ] spec「明确不做」清单里的东西一件没做；做了任意一件 = 本清单作废，重走 spec。

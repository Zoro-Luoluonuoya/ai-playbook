# Codex 子代理配置示例

> 这份东西解决一个问题：**把「我临场决定开几个分身」变成「配置文件说死」**。
> 在 WorkBuddy 里这套靠 AI 自觉，在 Codex 里可以落成 TOML——同样的方法，不同的执行载体。

---

## 先读这段（很重要）

**字段名以官方文档为准，内容照搬即可。**

我是按 2026 年的公开资料写的：`[features] multi_agent`、`[agents] max_threads / max_depth`、agent 定义放 `~/.codex/agents/` 或项目级 `.codex/agents/`。
如果哪天 Codex 改了键名，**只改壳子，`instructions` 里的内容不用动**——那部分才是这套方法的价值。

装之前先核对一遍：
1. `codex --version`（本文按 CLI 0.115+ 的能力写）
2. 官方仓库的 `config.toml` 示例
3. 用一个低风险任务试跑一次，看并发是不是真的起来了

---

## 三个角色，对应三种活

| 角色 | 干什么 | 关键约束 | 什么时候用 |
|---|---|---|---|
| `explorer` | 只读：定位代码、梳理依赖、回答"改这个会影响哪里" | 不许改任何文件 | 开工第一步；不确定影响面时 |
| `worker` | 实现：按 spec 写代码 + 自己跑该跑的验证 | 不许改 spec 之外的东西 | 拆分后互不相交的模块 |
| `reviewer` | 只读：查验证覆盖、契约一致性、边界条件 | 不许改文件，只出问题清单 | 合并前；交付前 |

**为什么是这三个而不是更多**：它们对应"看清 → 做完 → 验过"三个不重叠的职责。再加角色，就会出现两个 agent 对同一件事有不同意见——那正是口径漂移的来源。

## 怎么装

```bash
# 个人级（所有项目生效）
cp config.toml.example ~/.codex/config.toml     # 已有就手动合并，别覆盖
cp agents/*.toml   ~/.codex/agents/

# 项目级（只对这个项目生效，优先）
mkdir -p .codex/agents
cp agents/*.toml .codex/agents/
```

验证：随便给一个任务，看它是否会自己派 `explorer` 去查而不是直接动手。

## 与并行规则的关系

这套配置是 `PA1–PA4`（默认不开 / 三条件 / 开前告知 / 收工校对）在 Codex 上的**执行载体**：

| 规则 | 在 Codex 里怎么落 |
|---|---|
| PA1 默认不开 | `max_threads` 不要一上来拉满，从 2 开始 |
| PA2 三条件 | `worker` 的 `instructions` 里要求它先报"我要改哪些文件"，你据此判断块是否相交 |
| PA3 开前告知 | 在提示词里要求主 agent 先说"派几个、各做什么" |
| PA4 收工校对 | `reviewer` 的职责就是干这个——但**编号与数字的一致性还得你自己 grep**，agent 不会主动做 |

最后一句是重点：**能自动化的只有执行，判断还得你来。**

## 一个坑先说在前面

`max_depth = 1` 意味着子代理不能再派子代理。这看起来是限制，其实是保护——
两层嵌套之后，你无法追踪某个结论是从哪一层冒出来的，出了问题只能全部推倒重来。
**宁可多开平行的，不要加深嵌套的。**
